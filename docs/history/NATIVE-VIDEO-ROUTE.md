## Offline implementation investigation
The complete dynsym audit (not a filtered video-only symbol set) confirms factories for Screen, GF, Iow, CallbackVideo, NullVideo and Console. XML entries for EGL/NvMedia/NvVideo have no corresponding exported factory in this copied library. Initial overly narrow filter was corrected; do not infer absence from the filtered report.

Dynamic runtime dependencies found in original device library: Screen loads libscreen.so.1; GF loads libgf.so.1; Iow loads libiow.so.1. Code contains window class, source/destination sizing, window group and posting paths. String properties include hmi-window-class, video-window-class, video-layer-id. Availability of runtime libraries and usable display-service ownership must be checked before selecting one.

HmiMain3D has concrete code references for TerminalUI video service: requesting video channel at0x80ca475, viewport at0x80ca996, video sink setup at0x80cae58; layer enable at0x80c862e. These are string xrefs, NOT callable entry addresses or validated signatures. This gives a specific BMW integration path to investigate rather than arbitrary graphics initialization.

Artifacts: build/native-video-route-20261106/audit.json, hmi-video-xrefs.json, factory-disassembly.json. Factory disassembly is unrelocated ELF code; relocation values must be applied before inferring vtable addresses. No fabricated C++ ABI or vehicle code was executed.

## Vehicle results (2026-11-06, read-only inventory and bounded clip tests)
Evidence under `build/native-video-route-20261106/vehicle-20261106T155907/` (inventory, config, slog) and `build/native-video-test-20261106/vehicle-*/`.
- `io-media-cinemo.cfg` (stock): `plugin-video-device = "NmeDeviceScreen"`, `plugin-video-renderer = "NmeVmr"`, `video-hardware-decode/deinterlace/mix = 1`, `video-default-dest-rectangle = "0,0,800,480"`, `video-output-id 0` -> `video-window-class = CinemoVideo0_TaskA,CinemoVideo0_TaskB`, `video-subpicture-window-class = CinemoSubpicture0_TaskA,CinemoSubpicture0_TaskB`; output 1 -> `CinemoVideo1_*`. `plugin-unload-delay = 10`.
- Architecture CONFIRMED: `io-media-cinemo` and `NmeCmdLine` are clients of `io-nme` (`/dev/io-nme`); io-nme loads plugin classes on demand (only NmeBaseClasses mapped while idle) and unloads them after 10 s. Log lines: `NmeClassDevices Create(NmeDeviceScreen)`, `Register(NmeDeviceScreen) -> x?video-window-class=...&title=Cinemo Media Engine`.
- `libscreen.so.1` is in `/lib/graphics/tunnelcreek/` (with `libWFDtunnelcreek.so`); `/lib/graphics` has libWFD/libEGL/libKD. No `libgf` or `libiow` on the car, so only `NmeDeviceScreen` is usable. `/dev/screen` exists (screen service), `/dev/io-nme`, `/dev/msvdx`, `/dev/DisplayManager:0`, `/dev/WAL*`.
- Clip test through `NmeCmdLine` with software decode: 303-330 frames in 14.6-15.6 s (about 21 fps decode, 23-27 % CPU, 0 dropped), H.264 level 3.1, 800x480. `io-nme`, HmiMain3D and WalServer unaffected. A relative clip path produced 0 frames because io-nme opens the file itself.
- `DisplayManagerScreen` registers the window by class name and, with `-pre_cache`, applies cached visibility: new window -> `visible=no x=0 y=0 w=0 h=0 alpha=255 zorder=0 display=0`. Commands written to `/dev/DisplayManager:0` (`name,v,0|1;` `name,s,w,h;` `name,p,x,y;` `name,S/P` source, `name,a,alpha;` `name,D;`) are accepted and logged (`setting CinemoVideo0_TaskA/Dst-size to 800,480`). `D` only logs the transmission, not window details. With size 800x480 at 0,0 and visible=1 the user saw nothing while on the radio page; the HMI video layer is probably only enabled in a video context.
- `/opt/sys/etc/videocapture-NBT-B069_C1.cfg.*`: ADV7180 inputs -> FPGA VCAP (0x10ee) -> `SCREEN TASK A / TASK B` outputs (`TaskA:VideoCapture0`). The stock window classes `CinemoVideo0_TaskA/B` match these tasks. WAL statistics `#video` stayed 0 while our window existed.
- No stock file on the car contained the string `CinemoVideo0` (greps over /opt/sys, /opt/mm, /opt/hmi bin/lib/etc), so the HMI builds or receives the class names elsewhere. Next evidence needed: watch a STOCK video playback (USB video) and read `DisplayManagerScreen`, `io-nme` and WAL lines in sloginfo.
- Car tool gaps: no head, printf, env, rmdir, which on the car.

## Stock USB-video playback observed and reproduced (2026-11-06 evening)
- A USB video started from the HMI produces: `iom_attach_input(/fs/usb0///<file>)` and `iom_attach_output(display://video-output-id=1)` in io-media-cinemo, then io-nme `Register(NmeDeviceScreen) -> ?video-output-id=1&video-output-aspect-x=1&video-output-aspect-y=1&video-window-class=CinemoVideo1_TaskA,CinemoVideo1_TaskB&video-subpicture-window-class=CinemoSubpicture1_TaskA,CinemoSubpicture1_TaskB`. DisplayManagerScreen creates both windows (hidden, cached), then VideoApp (pid 49176) sets `Src-pos 0,0`, `Src-size 800,480`, `Deinterlace-mode 1`, `Visibility true`; dev-nvideocapture starts capturing (800x480, 60 Hz, NV24 surfaces) and WAL counts `#video = 60..61` per second. io-nme maps libscreen.so.1 and libNmeVideoSW.so (software decode, also in the stock case).
- A second window of the same class is rejected by DisplayManager (`multiple instances!`), so running our own NmeCmdLine next to the stock player does not work. The video layer of the HMI is only shown when the HMI itself is in a video context.
- Working integration: `src/android_auto/nbt_live_file.c` overlays `/fs/usb0/<file>` (the stock player opens it through io-nme) and serves raw H.264. First with a looped clip, then live from the FIFO (`--fifo`), fed on the car by `nbt_h264_feed` (phone stand-in). The HMI showed the moving test picture; when the source stops the picture freezes (the player holds about 5 frames, last sent frame 78 vs shown frame 73). Evidence logs in `build/native-video-test-20261106/`.
